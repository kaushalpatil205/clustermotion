# ClusterMotion (`cm`) Python Engine Commands

This document contains all the specialized `cm` (ClusterMotion) commands used to execute the zero-downtime migration of our database and traffic from the Blue cluster to the Green cluster.

## 1. Environment Setup

Before running `cm` commands, the environment needed to be configured to point to the correct state backend and clusters:
```bash
# Export the path to the clustermotion config generated during infrastructure deployment
export CM_CONFIG=/opt/clustermotion/engine/config.json
```

## 2. Generate and Apply Traffic Load

To simulate real-world e-commerce traffic on the Blue cluster while migrating:
```bash
# Generate background shop traffic continuously on the Blue cluster
cm load start --cluster blue --users 50
```

## 3. The Migration Execution

The core zero-downtime migration workflow was executed natively by the `cm` python program. 

### A. Pre-flight & Setup
```bash
# Validates the state of both clusters and establishes the Argo Workflow pre-flight check
cm preflight --from blue --to green

# Prepares the green database by syncing initial data (pg_dump / pg_restore)
cm db sync --from blue --to green
```

### B. The Automated Argo Workflow Switch
Instead of manually typing every switch command, we used the overarching `cm migrate` command which triggered the automated Argo Workflow to handle the database lock, replication, state sync, and traffic flip:
```bash
# Kicks off the Zero-Downtime Migration Argo Workflow
cm migrate --from blue --to green --steps 50,100 --hold 10 --approve-db auto
```
**Explanation:** 
- `--from blue --to green`: Denotes the origin and target clusters.
- `--steps 50,100`: Flips traffic in a canary release format (50% first, then 100%).
- `--hold 10`: Wait time between canary steps.
- `--approve-db auto`: Automatically applies the database switchover without requiring manual intervention.

### C. Manual DB Pointing (Fallback/Override)
During the workflow, if manual intervention was required for the Route53 DNS switch for the DB:
```bash
# Force Route53 to point the internal database DNS strictly to the Green cluster Postgres
cm db point --to green
```

## 4. Verification and Reporting

After the traffic completely migrated to the Green cluster, we used the verification commands to prove 0 data loss:
```bash
# Kill the load generator to stop sending requests
pkill k6

# Download the confirmed orders JSON generated by the shop during the test
cm verify --confirmed results/confirmed.jsonl --json-out results/verify.json

# Analyze the results and generate the migration proof report
cm report
```
**Explanation:** `cm report` outputs a statistical summary of all the HTTP requests, proving that out of thousands of e-commerce orders, **0 writes were lost** during the database switch.
